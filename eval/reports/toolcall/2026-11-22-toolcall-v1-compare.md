# 도구 호출 측정 toolcall-v1: 변형 비교(#103)

확인 묶음 toolcall-v1(120개)로 로컬 모델의 첫 도구 호출을 잰 주 결과입니다. 채점 규칙은 `contracts/eval/toolcall/README.md`, 채점기는 `eval/harness/toolcall.py`입니다. 묶음 해시는 계약 표(`contracts/eval/confirm-sets.md`)와 같았습니다(`bf7066b5…`, 파일 5개).

## 범위

- **변형은 개발 묶음 결과를 보고 정했습니다.** 개발 묶음(`agent/eval_dev/tool_calls.jsonl`, 60개) 비교(`2026-11-21-toolcall-dev.md`)에서 S0 local, 예시(fewShot) local, 외부 기준 external을 골랐습니다. 문법 강제와 전부 켬은 개발 묶음에서 gateway 60초 제한 초과 502가 많아(18/60, 20/60) 뺐습니다.
- **반복:** 실행 시간(GPU 대기열) 때문에 fewShot과 external은 1회만 돌렸습니다(사용자 결정, 결정 0007). 그래서 **주 비교는 세 변형의 1회차끼리(pass^1)**입니다. S0 local은 3회를 다 돌렸고 2·3회차와 pass^3은 부록입니다.
- 120개 전부(2단계 도구 `expense_request`·`purchase_request` 14개 포함)를 돌렸고, 1단계 소계를 따로 적습니다.
- 변형에 `thinking`은 보내지 않았습니다(개발 묶음과 같이 모델·스택 기본값).

## 실행 조건

- 기기: RTX 4070 SUPER 12GB, WSL2 Docker, Ollama 0.40.15(문맥 8192)
- 모델: `local`=qwen3.5:9b(digest 56671c2ab938, GGUF Q4_K_M), `external`=Claude Haiku 5.5
- 스택: develop `fe4aa1b`, postgres·fake-erp·erp·litellm·gateway(`GATEWAY_EVAL_TOOLCALL=1`)·agent(`AGENT_EVAL_MODE=1`), `PACK_STAGE=2`. setup이 있는 항목 24개는 erp를 초기화한 뒤 상태를 만들었습니다.
- llama-server 프롬프트 캐시 상한: S0 local은 기본 8192MiB, fewShot·external은 1024MiB(아래 실행 경위). 출력에는 영향이 없고 지연에만 영향이 있을 수 있습니다.

- **세 변형의 차이는 구간 안입니다.** 같은 항목끼리 짝지으면(실행 오류 뺌) S0 대 fewShot은 S0만 맞음 7, fewShot만 맞음 8(짝 118)입니다. S0 대 external은 S0만 15, external만 10(짝 119)입니다. 1회 결과로는 fewShot이 S0보다 낫다고 말할 수 없습니다. 개발 묶음에서 fewShot이 86%로 높았던 것은 같은 묶음에서 뽑은 예시로 같은 묶음을 잰 값이었습니다.
- 가장 약한 유형은 resolve(날짜·이름·수량을 풀어 씀)로, 세 변형 모두 절반 안팎입니다.
- 2단계 도구(14개)는 S0 7/14, fewShot 10/14입니다. 개수가 적어 구간이 넓습니다.

### external의 모델 위치

external 120회차 중 44회차는 `local`로 처리됐습니다. 인사(hr) 에이전트의 일부 요청은 업무 주제 로컬 강제로 외부 별칭을 요청해도 gateway가 로컬로 보냅니다. 위치별로 나누면 다음과 같습니다.

| 항목 묶음(external 실행의 모델 위치) | S0 local | fewShot local | external |
|---|---|---|---|
| 외부로 간 76개 | 59/76 | 60/75 | 63/76 |
| 로컬로 돌린 44개(hr) | 33/43 | 33/43 | 25/44 |

외부로 간 항목에서는 Haiku가 조금 높고, 로컬로 돌린 hr 항목에서는 external 실행이 S0보다 낮습니다. 로컬로 돌린 호출은 생각 단계를 끄는 등 경로가 다르지만(#434), 1회 결과라 원인은 나누지 않았습니다(탐색 거리).

## 실행 경위(측정에 넣지 않은 것)

- **S0 local 05:07 중단:** WSL 메모리 부족(OOM, 측정 밖 작업이 메모리를 같이 씀)으로 qwen 실행기가 죽어 72/360회차에서 멈췄습니다. 다시 시작한 이유는 OOM이고 결과 때문이 아닙니다. 부분 실행은 버리고 05:08에 처음부터 다시 돌렸습니다. 중단 전 05:01에 진행 확인으로 첫 28회차의 결과 분포와 오류 2건의 상태 코드를 본 적이 있고, 중단 뒤에는 버린 결과를 집계하거나 보지 않았습니다.
- **fewShot local 05:40 중단과 05:41 멈춤:** 다시 OOM이 났습니다(28/120회차). 원인은 llama-server 프롬프트 캐시(기본 상한 8192MiB)가 호스트 메모리에 쌓이는 것이었고, 리드가 Ollama를 `LLAMA_ARG_CACHE_RAM=1024`로 다시 띄웠습니다. 두 번째 시도는 그 재시작을 위해 멈췄습니다. 두 부분 실행은 열지 않고 버렸고, 05:42에 처음부터 다시 돌렸습니다.
- 버린 부분 실행 세 개의 sha256은 각 실행 보고서 메모에 있습니다.

## 공개 범위

문항은 저장소에 넣지 않습니다. 회차 기록(`.json`·`.rows.jsonl`)은 문항 내용이 드러나는 `result`(모델이 만든 인자)·`mismatched`·`schema_errors`를 빼고 `error`는 상태 코드만 남긴 사본이고, 실행별 보고서에서 인자 틀림 목록을 뺐습니다(`eval/tools/mask_toolcall.py`). 커밋 전에 세 파일 모두에서 문항의 발화와 기대 인자·setup 문자열 값(4자 이상, 도구 이름 등 공개 식별자 제외)이 0개인지 확인했습니다. 원본 sha256은 각 실행 기록의 `meta.notes`에 있습니다.
