## 결론

1. **기능은 갖췄고, 문제는 "읽기"입니다.** 정답 경로를 아는 스크립트는 12개 과업을 모두 끝냈습니다. 그러나 판단에 쓸 값(금액, 결재선, 상태, 사람)이 코드·키·ID로 보이거나 떨어져 있어 7개가 부분 성공입니다. 가장 심각한 것은 경비 정산 미리보기입니다. 영수증에서 읽은 금액을 사람이 확인해야 하는 자리에 `amount 42000`(실제 스택은 JSON 원문)이 나옵니다.
2. **결재자와 관리자에게 첫 화면이 맞지 않습니다.** 모두 채팅으로 들어오고, 결재 건수가 어디에도 없으며, 대결로 받은 문서는 별도 탭에 숨어 있습니다.
3. **결재·대결에 오류 예방이 약합니다.** 승인·반려가 한 번에 확정되고, 위임 기본값이 가장 넓은 범위이며, 해지도 확인이 없습니다.
4. **접근성 자동 점검은 이미 깨끗합니다.** 재설계는 이것을 지키는 쪽이고(목표 위반 0), 색 대비 판정 불가 152개 요소는 #563에서 직접 계산합니다.
5. **지금 화면의 장점은 지킵니다.** 실행 전 미리보기, 되돌리기, 만료, 되돌릴 수 없음 경고, problem+json 오류 문구는 이미 갖춰져 있습니다. 재설계는 이것들의 표시를 고치되 동작은 그대로 둡니다.

## 한계

- 가상 사용자입니다. 실제 직원의 업무 습관(예: 결재를 메일 알림으로 여는지)은 반영하지 못합니다.
- 스크립트는 최소 경로라 실제 사람의 클릭·시간보다 적게 나옵니다. 걸린 시간은 모의 서버의 지연(이벤트당 120ms) 때문에 쓰지 않았습니다.
- 모의 데이터는 실제 스택보다 표시가 낫습니다(E4·A1의 필드 이름). 그래서 기준선은 실제보다 후합니다.
- 데스크톱 폭만 봤습니다. 태블릿 폭은 재설계 뒤 더합니다.
