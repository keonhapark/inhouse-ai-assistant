# 지금 화면 기준선: 과업 걸어 보기

재설계 전 화면에서 페르소나 세 유형의 과업 12개를 걸어 본 결과입니다. 재설계 뒤(#564) 같은 스크립트로 다시 돌려 견줍니다.

**가상 사용자 결과입니다.** 두 가지를 했습니다.

1. **스크립트 걸어 보기(수치):** Playwright 스크립트가 화면에 보이는 이름(역할·라벨)으로만 요소를 찾아 조작하고, 클릭·입력·단계·성공 기준을 셉니다. 스크립트는 정답 경로를 알고 누르므로 "최소 조작 수"입니다. 사람은 이보다 더 헤맵니다.
2. **페르소나 관찰(질):** 결론을 모르는 서브에이전트가 페르소나가 되어 스크립트가 찍은 화면을 순서대로 보고, 어디서 망설이고 무엇을 잘못 읽을지 적었습니다. 원문은 [persona-review.md](persona-review.md)입니다.

## 1. 실행 환경과 재현

- web 모의 데이터 모드(msw)를 정적 빌드로 띄웠습니다(`ux/lib/serve.mjs`). 실제 모델·erp를 부르지 않습니다.
- Chromium headless 하나, 과업마다 새 브라우저 문맥(모의 데이터가 처음 상태로 돌아감). 창 크기는 페르소나 기기(직원 1280×800, 결재자 1920×1080, 관리자 1440×900).
- 재현: `cd ux && npm ci && npm --prefix ../web ci && npm run walk` → `research/walkthrough/baseline/`. web이 바뀌면 자동으로 다시 빌드하고, 결과에 잰 web 버전(커밋)을 남깁니다(이번 기준선은 `4988d0e`).
- 같은 명령을 두 번 돌려 결과가 같은 것을 확인했습니다.
- 조작 단계는 클릭·입력·키 단계 수입니다. 눈으로 찾는 단계는 스크립트마다 넣는 수가 달라 뺐습니다.
- 판정이 너그러워 거짓 통과하지 않도록 리뷰(테스트 분석 에이전트)를 거쳐 기준을 좁혔습니다. 예: 비용 통화는 "외부 비용" 열에서만, 감사 로그 이름은 "직원"·"에이전트"·"작업" 열에서만, 금지어만 보는 판정은 빈 글이면 실패. 버튼은 이름이 정확히 같은 것 하나만 누르고, 둘 이상이면 막힘으로 셉니다.

## 3. 읽는 법

- **막힌 과업은 없습니다.** 지금 화면은 기능이 다 갖춰져 있어 정답 경로를 알면 모두 끝납니다. 문제는 끝내는지가 아니라 **판단할 정보를 읽을 수 있는지**입니다. 12개 중 8개가 "부분 성공"이고, 못 채운 기준 9건 중 7건은 사람이 읽을 수 없는 값(코드 이름·API 필드·쉼표 없는 금액·ID), 2건은 화면에 없거나 떨어져 있는 정보(외부 전송 기록의 직원·대화, 운영 지표 표 근처의 기간)입니다.
- **조작 수는 적습니다.** 채팅이 일을 대신해 직원 과업은 클릭 1~3번입니다. 가장 많은 것은 A3(대결 위임) 조작 10단계·입력 4칸으로, 재설계에서 줄일 대상입니다.
- **모의 데이터가 실제보다 낫습니다.** E4·A1의 문서 상세는 모의에서 표시 이름(시작일·종류)이 나와 통과했지만, 실제 스택(`web/docs/images/real-inbox.png`)은 `start_date`·`leave_type` 키 그대로입니다. E1도 실제는 `id`·`formId`·`fields` JSON까지 나옵니다(`real-chat-attach-receipt.png`). 그래서 이 기준선은 **실제보다 후한 쪽**입니다. #556이 실제 스택을 고친 뒤 실제 스택 캡처로 다시 확인합니다.
- **스크립트가 못 보는 망설임**은 페르소나 관찰이 채웁니다. 대표적인 것:
  - 결재자의 첫 화면이 채팅이라 승인함을 찾아야 하고, 대결로 들어온 문서는 "내 차례"가 아니라 "대결" 탭에만 있어 놓칠 수 있습니다(A1·A2).
  - 관리 콘솔에서 "최근 24시간" 버튼이 눌린 채 날짜 칸은 7일 전부터를 가리켜, 지금 보는 기간을 잘못 읽을 수 있습니다(M1·M3).
  - 회의실 예약을 되돌리면 배지는 "되돌림"인데 문장은 "예약했습니다" 그대로입니다(E2).
  - 결재 대리인으로 고른 사람이 내 차례에 있는 문서의 요청자 본인이면, erp는 그 문서를 대리인의 대결함에서 뺍니다(`erp/.../DelegationAuthority.java`). 자기 결재는 막히지만, 위임 기간에는 그 문서를 처리할 사람이 없고 화면은 이것을 알려 주지 않습니다(A3).
  - 위임 미리보기를 눌러도 1080 높이에서 "등록" 버튼이 화면 밖에 있습니다(A3).
- **기준이 너그러운 곳:** M4의 "왜 달랐는지" 기준은 `부족 필수 도구 room_reserve를 실행하지 않음` 줄이 있어 통과했지만, 그 아래는 `dbAssertions[0] $.items[?(@.status=='confirmed')]` 같은 JSONPath입니다. 재설계 뒤에도 같은 기준을 쓰되, 보고서에는 이 점을 함께 적습니다.

## 4. 재설계 뒤 비교할 것(#564)

- 같은 과업 12개, 같은 성공 기준. 화면 이름이 바뀌면 `tasks.mjs`의 찾는 이름만 고치고, 고친 줄을 보고서에 적습니다.
- 목표: 부분 성공 0, 확인 기준 미달 0, A3 조작 단계 10 → 7 이하, 결재자 첫 화면에서 받은 결재 건수가 보임.
- 태블릿 폭(768×1024) 과업을 결재자 A1·A2에 더합니다.
