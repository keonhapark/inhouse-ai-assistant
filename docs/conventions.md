# 저장소 컨벤션

이 문서는 커밋, 브랜치, PR, 병합, 릴리즈를 어떻게 하는지 적습니다. 이 저장소에서 작업하는 모든 사람과 도구가 같은 규칙을 따릅니다.

## 1. 커밋 메시지

### 형식

```
<유형>(<모듈>): <요약>

<본문>

<꼬리>
```

- **요약:** 한국어 습니다체 한 문장이고 50자 안팎입니다. 끝에 마침표를 찍지 않습니다. 무엇이 바뀌었는지를 결과로 씁니다.
- **유형:**

  | 유형 | 쓰는 때 |
  |---|---|
  | `feat` | 기능 추가 |
  | `fix` | 버그 수정 |
  | `refactor` | 동작을 바꾸지 않는 구조 변경 |
  | `test` | 시험만 추가·수정 |
  | `perf` | 성능 개선 |
  | `contract` | `contracts/` 변경(OpenAPI, 스키마, 가짜 서버, 행동 계약 시험) |
  | `pack` | `packs/` 변경(업종 팩 설정·데이터) |
  | `docs` | 문서 |
  | `build` | 빌드·의존성 |
  | `ci` | CI 워크플로 |
  | `chore` | 그 밖의 잡무 |
  | `revert` | 이전 커밋 되돌리기 |

- **모듈:** 디렉터리 이름을 그대로 씁니다. 대상은 `erp`, `gateway`, `agent`, `rag`, `eval`, `web`, `incident`, `slack`, `contracts`, `packs`, `infra`, `docs`입니다. 여러 모듈에 걸치면 가장 중심인 것 하나를 쓰고, 본문에 나머지를 적습니다. 두 모듈 이상을 고쳐야 한다면 커밋을 나눌 수 있는지 먼저 봅니다.
- **본문(선택, 바뀐 이유가 요약만으로 안 보이면 씀):**
  - 요약과 빈 줄 하나로 띄웁니다.
  - 왜 바꿨는지, 무엇을 고려했는지, 버린 방법을 습니다체로 씁니다.
  - 한 줄은 72자 안팎에서 줄을 바꿉니다.
  - 관련 결정 기록은 `docs/decisions/NNNN-*.md`로 가리킵니다.
- **꼬리(선택):** `Refs: #<이슈 번호>`. `Co-Authored-By` 같은 도구 표시 줄은 넣지 않습니다.

### 예

좋은 예:

```
feat(erp): 회의실 동시 예약을 409로 거절합니다

같은 회의실·같은 시간대에 예약 두 건이 동시에 들어오면 유니크 제약으로
한 건만 저장하고, 나머지에는 problem+json 409를 돌려줍니다. 재시도는
클라이언트가 멱등 키로 합니다. 비관적 락은 처리량 때문에 쓰지 않았습니다
(docs/decisions/0004-room-concurrency.md).
```

```
contract(contracts): 대결 위임 조회 응답에 위임 범위 금액 한도를 더합니다
```

```
fix(gateway): 외부 요청 기록에 가림 전 원문이 남던 문제를 고칩니다
```

나쁜 예와 이유:

| 예 | 이유 |
|---|---|
| `update` | 유형·모듈·내용이 없음 |
| `feat: 여러 가지 수정` | 한 커밋에 여러 변경, 모듈 없음 |
| `feat(erp): 회의실 예약 기능 추가.` | 습니다체 아님, 마침표 |
| `fix(agent): 다날 면접용으로 라우터 수정` | 회사 이름 금지(6절) |

### 한 커밋 한 변경

- 커밋 하나에는 되돌렸을 때 의미가 하나인 변경만 담습니다.
- 서식 정리와 동작 변경을 섞지 않습니다. 이름 바꾸기와 동작 변경도 섞지 않습니다.
- 시험은 그 시험이 확인하는 변경과 같은 커밋에 둡니다.
- 생성된 파일(잠금 파일, 스냅숏)은 그것을 만든 변경과 같은 커밋에 둡니다.

## 2. 브랜치

| 브랜치 | 용도 | 만드는 곳 | 병합하는 곳 |
|---|---|---|---|
| `main` | 릴리즈만. 직접 커밋 금지 | | |
| `develop` | 통합. GitHub 기본 브랜치. 직접 커밋 금지 | | `main`(릴리즈) |
| `feat/<모듈>-<주제>` | 기능 | `develop` | `develop` |
| `fix/<모듈>-<주제>` | 버그 수정 | `develop` | `develop` |
| `contract/<주제>` | 계약 변경(프로젝트 리드만) | `develop` | `develop` |
| `pack/<업종>-<주제>` | 업종 팩 변경(프로젝트 리드, 4단계 팩 세션) | `develop` | `develop` |
| `docs/<주제>` | 루트 문서(프로젝트 리드) | `develop` | `develop` |
| `chore/<주제>` | 루트 잡무·CI·빌드(프로젝트 리드) | `develop` | `develop` |
| `hotfix/<주제>` | 릴리즈 뒤 `main`의 급한 수정. 기본은 쓰지 않고 다음 릴리즈로 고침 | `main` | `main`과 `develop` 둘 다 |

- 브랜치 이름은 영문 소문자, 숫자, 하이픈만 씁니다. 예: `feat/erp-room-concurrency`, `contract/delegation-scope`
- 모듈 세션은 `feat|fix|test|refactor|perf/<모듈>-<주제>`만 씁니다. CI가 브랜치 이름의 모듈로 담당 경로를 검사합니다(`docs/workflow.md`).
- 한 세션은 한 번에 한 작업 브랜치에서 일합니다. worktree는 `develop` 기준으로 만듭니다.
- 병합된 브랜치는 지웁니다.

## 2-1. 이슈

- 할 일은 GitHub 이슈로 관리합니다. 단계별 마일스톤(`1단계`, `2단계`, `3단계`, `업종 팩`)에 넣고, 라벨은 모듈(`erp`, `gateway`, `agent`, `rag`, `eval`, `web`, `incident`, `slack`, `contracts`, `packs`, `infra`)과 종류(`feature`, `bug`, `contract`, `decision`, `blocked`)를 붙입니다.
- 이슈 제목은 습니다체 한 문장입니다. 본문에 배경, 완료 조건, 담당 경로를 적습니다.
- 앞선 이슈가 끝나야 시작할 수 있으면 본문에 `blocked by #<번호>`를 적고 `blocked` 라벨을 붙입니다. 별도 의존 그래프 도구는 쓰지 않습니다.
- 작업 브랜치 하나는 이슈 하나를 맡고, PR 본문에 `Closes #<번호>`를 적어 병합 때 닫히게 합니다.
- 계약 변경 요청과 사용자 결정이 필요한 것도 이슈로 올립니다(라벨 `contract`, `decision`).

## 3. PR

### 제목

squash 병합 때 PR 제목이 그대로 `develop`의 커밋 메시지가 되므로 1절 형식을 지킵니다.

예: `feat(erp): 부재 시 대결 위임과 기간·범위 검사를 추가합니다`

### 본문 양식(`.github/pull_request_template.md`)

```markdown
## 무엇을 왜

<무엇을 바꿨고 왜 바꿨는지 두세 문장>

## 바뀐 것

- 

## 시험 결과

- 실행한 명령과 결과(통과 n / 전체 m). 실패나 건너뛴 시험은 이유와 함께 적습니다.
- 계약 시험: 통과 / 해당 없음

## 계약 영향

- 없음 / 하위 호환 변경 / 하위 호환을 깨는 변경(oasdiff 결과 붙임, 프로젝트 리드 확인 필요)
- 계약 변경 요청을 했다면 `docs/contract-requests.md`의 항목

## 담당 경로 밖 변경

- 없음 / 있음(이유. 이 경우 PR 검사가 실패하므로 프로젝트 리드 확인 필요)

## 리뷰에서 고친 것

- 사람이나 리뷰 에이전트가 잡은 버그, 뒤집은 결정, 다시 쓴 부분. 없으면 "없음"이라고 적습니다.

## 확인 못 한 것·남은 일

- 

## 사용자 결정

- 필요 없음 / 필요(`docs/decisions/NNNN-*.md`)
```

- PR 하나에는 브랜치 하나, 주제 하나만 담습니다. 리뷰할 수 있는 크기(바뀐 줄 400줄 안팎)를 넘으면 나눕니다. 생성 파일은 줄 수에서 뺍니다.
- 필수 체크(항상 도는 요약 job)가 통과해야 병합할 수 있습니다.

## 4. 병합 방식

| 병합 | 방식 | 근거 |
|---|---|---|
| 작업 브랜치 → `develop` | **squash 병합** | 에이전트 세션은 작은 커밋을 많이 만듭니다. squash하면 `develop`의 커밋 하나가 PR 하나에 대응하고, 되돌릴 때 `git revert` 한 번이면 됩니다. 메시지 형식도 PR 제목 한 곳만 지키면 됩니다. 브랜치 안의 세부 커밋은 PR 페이지에 남습니다 |
| `develop` → `main` | **병합 커밋**(`--no-ff`, squash 금지) | `main`에 `develop`의 PR 단위 이력을 그대로 남겨, 태그에서 어떤 PR이 들어갔는지 추적합니다. squash하면 `develop`과 `main` 이력이 갈라져 다음 릴리즈 때 충돌이 납니다 |
| rebase 병합 | 쓰지 않음 | 공유 브랜치 이력을 다시 쓰지 않습니다 |

- **각 모듈 세션이 자기 PR을 `develop`으로 squash 병합합니다.** 조건은 필수 검사 `ci-summary` 통과입니다. `ci-summary`는 자기 모듈 시험, 계약 시험, 담당 경로 밖 변경 검사, 비밀값 검사를 묶습니다. `develop`·`main`은 브랜치 보호로 직접 push를 막습니다.
- 프로젝트 리드(S0)는 `contract/*`·`pack/*` PR, 루트 파일, 충돌 정리, `develop` → `main` 릴리즈를 맡습니다.
- 병합 순서: `contract/*`가 먼저입니다. 그 뒤 작업 PR은 `ci-summary`를 통과하면 순서 없이 병합합니다.
- 충돌은 먼저 병합된 쪽을 유지하고, 뒤 PR이 `develop`을 다시 받아 맞춥니다.
- squash 병합 커밋 메시지의 본문은 PR의 "무엇을 왜"를 옮깁니다. GitHub 기본값인 브랜치 커밋 목록은 지웁니다.

## 5. 릴리즈

- 단계 끝에 `develop` → `main`을 병합 커밋으로 합치고, `main`에 주석 태그를 답니다.
- 태그: `v0.<단계>.<수정>`
  - `v0.1.0`: 1단계
  - `v0.2.0`: 2단계
  - `v0.3.0`: 3단계
  - `v0.4.0`: 업종 팩
  - 릴리즈 뒤 hotfix는 `v0.1.1`처럼 수정 번호를 올립니다.
- 태그 조건은 셋입니다: 끝에서 끝 시험 통과, 평가 보고서 커밋, 계약 시험 통과.
- 태그 메시지와 GitHub Release 본문(습니다체)에 넣는 것:
  - 단계 요약
  - 평가 보고서 경로
  - 확인 셋을 돌린 커밋 해시
  - 알려진 한계
  - 공개 데이터·모델 라이선스 표기
- 저장소는 비공개입니다. 공개 전환은 따로 승인받습니다(`공개.md`).

## 6. 금지

커밋, 브랜치, PR, 이슈, 코드, 데이터, 문서 어디에도 아래를 넣지 않습니다.

| 금지 | 범위와 이유 | 대신 |
|---|---|---|
| 지원하는 회사·공고의 이름 | 저장소는 특정 회사용이 아닙니다 | 업종 이름(제조, 금융, IT 서비스) |
| 가상 회사에 실제 회사 이름·브랜드 | 실제 조직으로 오해받을 수 있습니다 | 지어낸 이름. 출처 인용은 README 근거 절에서 공개 기술 글 제목·URL로만 |
| 실제 사람의 이름·연락처·이메일·사번 | 개인정보입니다. 커밋 작성자도 해당합니다 | Faker(`ko_KR`, 시드 고정) 생성 데이터, 7절 noreply 주소 |
| 키 값 | API 키, 토큰, 비밀번호, 법제처 인증값(OC), JWT 서명 키 | `.env`(gitignore), `.env.example`에는 이름만. CI의 `secrets` job이 gitleaks(MIT)로 PR마다 검사합니다 |
| 확인 셋 원문 | 작업 공간 밖에 둡니다(기획서 측정 설계) | 해시만 커밋 |
| 모델 가중치·대용량 데이터 | EXAONE 1.2B는 비상업 라이선스이고, 용량 문제도 있습니다 | 내려받기 스크립트와 SHA-256 |
| 실제 사내 문서 | 공개 규정(법령·행정규칙)과 생성 문서만 씁니다 | `packs/*/docs.yaml`에 출처·라이선스 |

## 7. 커밋 작성자

- 작성자 이메일은 GitHub noreply 주소만 씁니다: `180478650+keonhapark@users.noreply.github.com`
- 저장소 안에서 설정합니다(전역 설정을 바꾸지 않음).

  ```
  git config user.name "keonhapark"
  git config user.email "180478650+keonhapark@users.noreply.github.com"
  ```

- GitHub의 "Block command line pushes that expose my email"을 켜 두기를 권합니다.
- 각 구현 세션 worktree도 같은 설정을 씁니다. `scripts/check-author.sh`를 pre-commit 훅으로 걸면 작성자 이메일이 noreply가 아닐 때 커밋을 막습니다(`ln -sf "$(pwd)/scripts/check-author.sh" "$(git rev-parse --git-path hooks)/pre-commit"`).

## 8. 문체와 기록

- 공개 문서(README, `docs/`, 커밋 메시지, PR·이슈 본문, 템플릿)는 습니다체로 씁니다. 명령조·훈계조는 쓰지 않습니다.
- 결정 기록: `docs/decisions/NNNN-<주제>.md`. 결정, 고른 이유, 버린 대안, 정한 사람(사용자 / 세션)을 적습니다.
  - 사용자가 정하는 설계 지점 6개(기획서 5-7)도 여기에 둡니다.
- 계약 변경 요청: `contract` 라벨 이슈를 올리고 `docs/contract-requests.md`에 날짜, 요청 모듈, 바꿀 것, 이유를 한 줄 적습니다. 프로젝트 리드가 `contract/*` PR로 반영하고 링크를 답니다.
