# 도구 호출 측정 항목 형식(toolcall-v1)

#103 도구 호출 측정의 항목 형식과 채점 규칙입니다. 확인 묶음(toolcall-v1) 작성자가 정한 형식이고, 문항은 저장소 밖에 있습니다(해시는 `../confirm-sets.md`). 형식은 `item.schema.json`입니다. 개발 묶음(`agent/eval_dev/`)도 이 형식을 따릅니다.
## 필드

| 필드 | 뜻 |
|---|---|
| `id` | `tc-001`~`tc-120` |
| `targetTool` | 이 항목을 셀 도구. 도구마다 5개 이상이 되도록 나눴습니다. 정답 행동의 도구와 다를 수 있습니다(예: 회수하려는데 ID가 없으면 정답은 목록 조회) |
| `category` | `direct`(그대로 부르면 됨), `clarify`(되묻기가 맞음), `confusable`(비슷한 도구 사이에서 헷갈림), `resolve`(날짜·이름·수량을 풀어 써야 함) |
| `requester` | 요청 직원 ID(`packs/manufacturing/fixtures/employees.json`) |
| `referenceDate`, `referenceWeekday` | 대화하는 날. "내일", "다음 주 금요일"은 이 날을 기준으로 풉니다. 세 날짜만 씁니다: 2027-03-10(수), 2027-04-14(수), 2027-05-21(금) |
| `utterance` | 직원의 한 턴 발화 |
| `setup` | (선택) 대화 전에 만들어 둘 상태. 시나리오 스키마의 setup과 같은 모양이고 `saveAs` 결과를 `${이름}`으로 씁니다. 발화와 정답 인자의 `${이름}`도 같은 값으로 바꿉니다 |
| `expected` | 정답 행동. `{"type": "call", "tool", "args"}` 또는 `{"type": "clarify", "missing": [인자 이름]}` |
| `alsoAcceptable` | (선택) 정답과 똑같이 맞다고 볼 다른 행동 |
| `argMatch` | (선택) 인자별 비교 방법. 없으면 `exact` |
| `note` | (선택) 왜 이 정답인지 |

## 채점 규칙(제안)

- **첫 행동만 봅니다.** 에이전트가 이 턴에서 처음 부른 도구와 인자, 도구를 부르지 않았다면 되묻기 여부를 봅니다.
- **call 정답:** 도구 이름이 같고, `expected.args`에 있는 인자가 모두 `argMatch` 기준으로 맞으면 맞음입니다.
  - `exact`: 값이 같음. 날짜·시각은 같은 시점이면 같다고 봅니다(`+09:00`과 UTC 표기 차이는 무시).
  - `date`: 값을 +09:00으로 바꾼 뒤 날짜 부분만 비교합니다(대결 시작·끝 시각은 회사마다 달라서). `endsAt`은 정답 날짜이거나 다음 날 00:00:00이면 맞습니다.
  - `set`: 배열을 순서와 무관한 집합으로 비교합니다(`formTypes`).
  - `normalized`: 공백과 영문 대소문자를 무시하고 비교합니다(발화에 그대로 나온 가맹점 이름).
  - `nonempty`: 빈 문자열이 아니면 맞음(사유, 제목, 검색 질문처럼 표현이 여러 가지인 값).
  - `ignore`: 보지 않음.
  - `expected.args`에 없는 선택 인자(예: `attendees`, `minCapacity`, `status`)는 넣어도 틀리지 않습니다. 단 정답에 없는 필수 인자를 지어내면 그 값이 발화에 근거가 있는지 따로 봅니다(지어낸 값 수를 보조 지표로 제안합니다).
- **clarify 정답:** 쓰기 도구를 부르지 않고 되물으면 맞음입니다. 되묻기 판단은 `eval/protocol.md` 2절 규칙(물음 모양으로 끝나는 줄)을 따릅니다. `missing`은 물어야 할 인자이고, 질문이 그중 하나 이상을 다루는지는 보조로 봅니다.
- 되돌릴 수 없는 도구(`risk: irreversible`, 즉 `approval_withdraw`, `delegation_revoke`)가 정답인 항목은, 도구를 부르기 전에 대상이 맞는 확인 질문("이 결재를 회수하면 되돌릴 수 없는데 진행할까요?")을 하는 것도 맞음으로 셉니다. 이 경우는 "확인 후 진행"으로 따로 집계합니다.
- `alsoAcceptable`의 행동과 같으면 맞음으로 셉니다. 정답과 대안을 따로 집계하면 어느 쪽으로 처리했는지 볼 수 있습니다.
- 1단계 측정에서는 2단계 도구(`expense_request`, `purchase_request`) 14개를 빼고 106개로 셀 수 있습니다. `targetTool`과 `contracts/mcp/tools.json`의 `stage`로 거릅니다.
